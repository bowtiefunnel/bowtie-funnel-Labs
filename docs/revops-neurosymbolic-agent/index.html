Technology stack

What each piece actually is, and which mile of the loop it belongs to — same color key as everywhere else in this document.

TechnologyMileRole in this system
Trigger.dev SDK v4 Orch. Durable task execution. wait.createToken / wait.forToken suspend a run at the human gate and resume it later without losing state — the run can sit for hours and cost nothing while parked.
TypeScript · Node 22 Orch. Type-checked task code end to end. Node 22 specifically — the Supabase realtime client needs native WebSocket, which Node 21 doesn't expose.
Supabase — Postgres + pgvector Symbolic All 7 tables: audit trail, tunable policy rules, verified session facts, pgvector semantic memory, the HITL ledger, and the two demo deal/task records.
Zod · zod-to-json-schema Symbolic The RevOpsAction discriminated union and validateBusinessPolicies(). JSON Schema generation constrains the model's output at the API level, not just after the fact.
OpenRouter Neural One API for both model tiers (Claude Sonnet, Gemini Flash) — a single integration instead of two provider SDKs.
llm-switchboard Neural Local, <1ms prompt classifier. Routes first-mile parses to the cheap tier, retries and narration to the premium tier.
Langfuse Orch. Per-call generation traces and real USD cost, rolled up per run — the numbers in §6's cost column come from here.
Slack — Block Kit Human The editable review card itself: Approve / Reject / Edit & approve, plus the deny-reason and edit-JSON modals.
btf-agents-gateway (Vercel) Human The production Slack Interactivity endpoint. Detects a waitpoint_-prefixed token and completes it via Trigger.dev's raw REST API — a separate repo, zero new dependencies.
Vitest Orch. 129 tests across action schemas, policy validation, model routing, and card construction.
Designed in, not active

OPENROUTER_BASE_URL is an env-level hook so an OpenAI-compatible privacy proxy (CloakPipe) can sit in front of every LLM call. It's wired into openrouter.ts but currently unset — direct OpenRouter, no redaction layer, in every run recorded in §6.

Dotted edge = the one place control returns to the task. btf-agents-gateway lives in a separate repo (no shared code — it can't import this repo's Zod schemas), so it detects a waitpoint_-prefixed token itself and completes it via Trigger.dev's raw REST endpoint. This exact edge — card → gateway → REST completion → resumed run — is what all 5 runs in §6 exercised.

§4

Workflow — the 3-Mile Loop

Every invocation runs this exact sequence, in order — drawable before runtime, which is what put this agent on the deterministic side of Gate 2 for everything except the two neural steps.

StepMileWhat happensReadsWritesComponent
1Trigger
 Symbolic Validates the incoming payload (Zod). — agent_executions (upsert) revops-action.ts
2Load context
 Symbolic Pulls enabled policy rules, recent verified facts, semantic memory. policy_rules, agent_session_logs, agent_memory_vectors — db.ts
3Parse → action
 Neural Cheap model tries first; escalates to premium on retry. ≤3 attempts, exact Zod errors fed back on failure. instruction + context agent_executions.parsed_action, .parse_attempts switchboard.ts, openrouter.ts, actions.ts
4Validate policy
 Symbolic Deterministic rule check, sub-millisecond, zero LLM calls. policy_rules — (violations held in memory, not persisted separately) actions.ts
5Human gate
 Human Posts the editable Slack card with the ledger's confidence rate; suspends the run on a waitpoint token. human_approvals (confidence query) human_approvals (insert), agent_executions.status hitl.ts, blocks.ts, btf-agents-gateway
6Execute
 Symbolic Absolute-value write; before/after captured straight from the returned row. revops_deals / revops_tasks revops_deals / revops_tasks revops-action.ts (executeAction)
7Write memory
 Symbolic Verified fact + optional embedding, written by code from step 6's returned rows — never by the LLM. — agent_session_logs, agent_memory_vectors db.ts
8Narrate
 Neural Premium model summarizes; instructed to quote only the provided numbers, never compute one. action, before/after, decision agent_executions.narration openrouter.ts, switchboard.ts
9Finalize
 Symbolic Records final status, USD cost, trace id. — agent_executions (status, cost_usd, completed_at) revops-action.ts, trace.ts
Note — policy breaches are not retried

The self-correction loop at step 3 only fires on schema errors. A policy violation means the model parsed correctly but the requested action breaches a rule — retrying would just teach it to launder the request. That case skips straight to step 5 with the violation message attached, never back to step 3.

§5

The learning loop

A separate mechanism from the workflow above — it doesn't run per-invocation, it runs across invocations. Every decision in step 5 lands in the human_approvals ledger; the ledger is the evidence for how much autonomy the agent has earned.

RungPromotes whenBehaviorDemotes when
1 · Per-item
current state		 Default for a new agent or a new action category Every decision — approved, rejected, or edited — goes through a human. No exceptions. — (starting rung)
2 · Batch review Confidence ≥90% over ≥20 decided items in that category One decision can cover a batch of same-category actions at once Rolling-window (last 20) approval rate drops below ~80% → back to Rung 1
3 · Spot-check Sustained confidence past Rung 2 Agent proceeds automatically; human samples a subset. Every action still lands in the ledger and stays reversible. Same rolling-window rule → drops back one rung
Never-graduate — Outward-publishing or irreversible actions keep a permanent per-item gate, regardless of confidence —
Current real state

The ledger now holds 5 decided items: 2 approved, 2 approved with edits, 1 rejected — 80% "good" rate (approved + edited, since an edit is still a completed action; rejected is not). Still nowhere near the 20-item, ≥90% threshold for Rung 2. Every action type stays at Rung 1: GATE_CLEAN_ACTIONS = true in code, matching the ledger's actual evidence — and correctly so, since 5 test clicks from one operator isn't a trust signal yet.

Known gap — confidence is agent-wide, not per-category yet

getApprovalConfidence() today computes one rate across every action type. The ladder is designed to run per action_type (a 95% rate on schema fixes shouldn't hide a 50% rate on discount overrides) — that slice isn't built yet; it's explicitly called out as out-of-scope in the plan until there's enough ledger data to make it meaningful.

What this confirms

Parse → policy gate → Slack posting → waitpoint suspension → btf-agents-gateway completing the token via raw REST → run resumption → deterministic execution → verified-memory write → narration — exercised end to end, 5 times, across every branch of the human gate. Run 5's rejection is the clearest proof the gate is real: the 60% request produced zero writes, not a quiet no-op.

§7

What shipped, by component

  • db 7 Supabase tables in 001_neurosymbolic_schema.sql — audit trail, verified session memory, tunable policy rules, pgvector semantic memory, the HITL ledger, and two demo execution targets. Applied and verified live.
  • routing llm-switchboard wrapped in agent/lib/switchboard.ts — fast tier for first-mile parses, premium tier for retries and narration, both tier tables configured to avoid the package's placeholder-model gotcha.
  • hitl editableReviewCard() adds a third "Edit & approve" button to the Slack card — verified twice in production, both times executing the corrected value instead of the original.
  • ledger agent/subagents/revops/hitl.ts — the per-item approval gate, posts the confidence rate on every card, writes every decision to human_approvals. Verified: 5 real decisions recorded (2 approved, 2 edited, 1 rejected).
  • gateway btf-agents-gateway (separate repo/Vercel project) — added waitpoint-token detection and raw-REST completion, zero new dependencies, every existing SEO/GEO Supabase-card path left untouched. Carried all 5 verification runs without a single misroute.
  • core agent/subagents/revops/revops-action.ts — the task itself, tying all nine steps together with idempotent execution-key upserts so a retried run never duplicates a Slack card or a database write.
